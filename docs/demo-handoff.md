# Demo handoff — 女将の右腕 (Okami no Migiude)

## 1. What this is

Okami no Migiude ("the okami's right hand") is a bilingual (JP/EN) municipal support portal for small businesses: an owner signs up, gives consent, and is interviewed in the browser by the ElevenLabs voice agent (Shima Enaga) over a server-minted WebRTC session; the transcript flows through an HMAC-verified post-call webhook into a Dify report engine, the owner gets a private report to view and download plus one ready email, and can request an advisor consultation that designated staff see in their queue. The demo story follows a fictional family-run onsen inn in Jozankei, Sapporo City (札幌市) — the owner copies bookings from several platforms into a notebook to plan room cleaning, and the report maps that workflow against a shared-calendar alternative. Without any live credentials the same journey still runs end to end on labeled substitutes (rule-based report, local `.eml` outbox), which is what the automated verification path exercises; every substitute is labeled in the UI rather than hidden.

## 2. Run it locally

Node 26 (built-in SQLite, `node:sqlite`) and npm 11. From the repository root:

```bash
npm ci            # or: npm install
cp .env.example .env
npm run build
npm start
```

- `npm start` runs `node --env-file-if-exists=.env scripts/start.mjs` (package.json), so `.env` is picked up automatically; `npm run dev` is the dotenvx-wrapped Nuxt dev server.
- The server binds `127.0.0.1` and serves on port **3000** unless `PORT`/`HOST`/`NITRO_HOST` say otherwise (`scripts/start.mjs` forces loopback unless `NITRO_HOST`/`HOST` is set).
- Open `http://localhost:3000` and use the exact origin configured as `PUBLIC_BASE_URL` (README.md).
- `DATA_DIR` (default `.data`) holds everything the demo writes: the SQLite database at `${DATA_DIR}/app.db` (created and migrated at boot, `server/utils/db.ts`) and the local mail outbox at `${DATA_DIR}/mail-outbox/` (`server/mail/index.ts`, `server/mail/local.ts`). Point `DATA_DIR` at a fresh subdirectory for a rehearsal instead of deleting working data. The test harnesses never touch it: `tests/browser-journey.mjs` spawns its own server on a free loopback port with a synthetic `DATA_DIR` under `tests/.data/test/<pid>`.

### Environment variables (from `.env.example`, each verified against the code)

**Required for the demo: none beyond the defaults.** With an empty `.env` the demo path needs no credentials: the database and outbox paths default under `DATA_DIR`, mail stays in the local outbox, and every live surface shows its honest unavailable state. - `PUBLIC_BASE_URL` is **required for production** (and any non-loopback demo host): the same-origin write guard `assertSameOrigin` (`server/utils/origin.ts`) compares the browser's `Origin` header against `publicBaseUrl().origin`, and a mismatch rejects browser writes with 403. Production currently serves `https://shima.musub.io` without it, so every browser write 403s until the deployment env sets `PUBLIC_BASE_URL=https://shima.musub.io` (diagnosed; fix not yet deployed).
- Every variable above is **verified-by-code** at the cited location; none is doc-only. Two discrepancies found while verifying (reported, not fixed — `.env.example` has another owner): the template's former `INTEGRATION_BASE_URL`/`INTEGRATION_TOKEN` pair had no reader anywhere in the code (inert; `tests/api-journey.test.mjs` proves setting them changes nothing) and was removed from the template in `85e1ed9` during this session; conversely `JMA_BASE_URL`, read by `server/snow/jma.ts`, is code-only and missing from the template. `WORKER_POLL_MS`/`CLOCK_OFFSET_MS` (`server/utils/env.ts`) are deliberate QA knobs with no HTTP backdoor.

## 3. The demo journey (presenter walkthrough)

Use a fictional family-run inn in Jozankei; only invented data. Follow [owner-journey-scorecard.md](../scorecards/owner-journey-scorecard.md) for the full check list.

1. **Homepage + language** — the portal explains the assessment; the selector switches Japanese ⇄ English and persists (cookie `app-locale`).
2. **Owner signup** (`/signup`) — required: owner name, email, business name, municipality (**Sapporo City / 札幌市** for the demo), password (≥ 8 characters), profile language (JA/EN — sets the report and ready-email language). Optional (任意): contact phone, business website, task note. No business-type field.
3. **Consent gate** (`/interview`) — the page explains the Shima Enaga interview and asks three approvals: recording/transcription handling, automated report processing, staff access. Start stays disabled until all three; no conversation is minted or started before consent — no `/api/interviews/start`, no `/api/voice/sessions` (`browser check interview.consent-gate`).
4. **Agent conversation** — **the ElevenLabs agent must be configured for this step** (`ELEVENLABS_API_KEY` + `ELEVENLABS_AGENT_ID` + `ELEVENLABS_WEBHOOK_SECRET`; `GET /api/voice/config` answers `agentAvailable: true`). After consent the page mints a WebRTC conversation token (`POST /api/voice/sessions`) and starts the conversation with `Conversation.startSession` (`@elevenlabs/client`) using the proven `/voice` argument shape: WebRTC, `stripAudioTags`, the profile-derived business context sent only as a complete pair plus `web_intake_complete`, and an English language override when needed. No interview-specific dynamic variables are sent; the server records the conversation↔interview association at mint for the webhook match. During the call the page renders a live transcript from the SDK's message callbacks — agent and owner turns verbatim, plus labeled system rows announcing the research handoff — while the authoritative transcript still arrives through the post-call webhook. There is no UI timer — length is agent-managed, and the page's end action ends the call early (`endSession`). Without the agent configured the page shows the honest unavailable state and no scripted sample UI (`interview.agent-unavailable`). Headless rehearsal fallback that needs no credentials: `POST /api/interviews/start` `{consent: true, mode: 'demo'}` then `POST /api/interviews/:id/complete` `{transcript}` feeds the rule-based analyzer (`server/analyze/index.ts`).
5. **Report preparation** — submission starts the background worker (`server/worker.ts`); the owner can leave and return. While the live Dify assessment runs the report is preparing; without `DIFY_API_KEY` a live interview stores the transcript, submits, and shows the honest unavailable state — no report, no ready mail (`interview-live.test.mjs`).
6. **Ready email** — one owner mail and one per designated staff address per ready report. On the default outbox path each is an `.eml` file at `${DATA_DIR}/mail-outbox/<mailId>.eml`; the body links `/reports/<id>`.
7. **Report view/download** (`/reports/<id>`) — current vs proposed workflow diagrams, ranked recommendations, time/cost estimates. The demo report is labeled 自動下書き（ルールベース） ("automated draft (rule-based)"); a Dify-generated report is labeled with its generator instead. Download is `report-<id>.md`; another owner gets 404, a signed-out visitor is redirected to `/sign-in?next=/reports/<id>`.
8. **Consultation request** — the owner requests follow-up; the page replaces the button with a recorded timestamp and a repeat click does not error (idempotent).
9. **Staff side** — staff accounts cannot self-register: they are provisioned at boot from `STAFF_EMAILS`/`STAFF_PASSWORD` (`server/plugins/boot.ts`; the roster skips an email that already belongs to an owner account). Staff sign in and open `/staff`: the queue lists all reports newest-first with owner contact and the consultation flag; staff cannot start an interview (notice on `/interview`) and cannot request consultations.
10. **Snow-day page** — `/snow` (`app/pages/snow.vue`, upstream PR #3): a JMA warning for the inn's area (or a built-in simulate mode) produces one draft per arriving guest to edit, approve and send; out of scope for the core demo walkthrough.

## 7. Known limitations

- No phone-call interviews — the interview is the browser-embedded agent only.
- No 3D avatar.
- No CRM integration.
- No live weather or transit feeds beyond the snow-day page's JMA warning/simulate; transit is out of scope entirely.
- No execution of recommended automations — the report recommends, the owner decides; implementation is a separate engagement (S5).
- Publication permission for real interview quotes or screenshots in the pitch is a separate team decision (PROJECT.md, report access and privacy).
- The public engineer board is stretch work after the owner and staff paths (PROJECT.md, MVP boundaries).
